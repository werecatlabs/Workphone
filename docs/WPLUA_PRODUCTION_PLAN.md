# Workphone Lua scripting production review and implementation plan

Reviewed: 10 October 2026 in `G:\Workphone`, source baseline `7107f0a393a889db82e28f91c25c32ba75104a26`.

Status: review and proposed implementation plan. The current scripting system has useful, working foundations, but is not production ready across runtime safety, reload, debugging, Editor authoring and distribution. This document does not implement those changes or certify an interactive debugging session.

Implementation has started since this baseline review. See [current implementation status and usage](WPLUA_IMPLEMENTATION_STATUS.md) for completed foundations, configuration, validation and remaining gates. The source findings below describe the reviewed baseline rather than claiming every issue still exists unchanged.

Scope: `WPLua`, `WPLuaBind`, Script components and invokers, application/project loading, Lua Editor windows, script authoring and assets, `Tools/csharp/LuaDebuggerVsix`, the separate C `WorkphoneScript` host, testing and packaged applications. Shared identity, cooking and asset publication use the [resource and asset plan](WPRESOURCE_ASSET_PRODUCTION_PLAN.md). Integrate with the [animation](WPANIMATION_PRODUCTION_PLAN.md), [physics](WPPHYSICS_PRODUCTION_PLAN.md) and [graphics](WPGRAPHICS_PRODUCTION_PLAN.md) plans rather than creating alternative engine systems.

## 1. Production outcome and release scope

A developer must be able to create a script, obtain useful completion and diagnostics, attach it to an actor, edit typed properties, save a scene/prefab, enter Play, debug the actual executing code, reload safely, return to the authored scene, and ship an application with the same supported behavior. A faulty script must produce an actionable diagnostic without corrupting its peers or losing the last working project/runtime state.

| Release | Required outcome |
|---|---|
| **R1: production foundation** | Windows x64, pinned Lua/Luabind ABI; protected execution and explicit ownership; deterministic component lifecycle; typed persisted script properties; project-scoped modules and asset identity; safe replacement with last-good recovery; responsive Editor Play/Stop and debugging; usable source editing and diagnostics; installable Visual Studio extension using normal debugging UI; attach/launch, breakpoints, pause/continue, step in/over/out, stack/scopes/variables/watch and exception stops; profiling and execution/memory budgets; reproducible packages; automated and interactive release evidence |
| **R2: comprehensive system** | R1 plus richer language services and refactoring, conditional/hit-count/function breakpoints and logpoints, controlled variable editing and evaluation, advanced coroutine inspection, dependency-aware selective reload, richer property schemas/migration, script profiling/allocation analysis, headless test tooling, multiple worlds/VMs where validated, opt-in remote debugging and an extension SDK. Every feature includes persistence, failure handling and acceptance evidence |
| **Separate extensions** | Hostile third-party mod execution, native/Lua unified mixed stacks and seamless native stepping, reverse/time-travel debugging, collaborative editing, remote build infrastructure and additional platforms. These require their own design and evidence and do not silently enter the supported matrix |

R1/R2 stage delivery of the requested comprehensive scope; an R2 item remains open until implemented and tested. Existing Lua gameplay, sample and Editor classes remain supported through compatibility adapters. Do not replace Luabind wholesale before the existing contracts and migration tests exist.

## 4. Proposed architecture and contracts

### 4.1 Ownership and service boundaries

Retain `IScriptManager` as a compatibility facade. Add explicit services/value types behind it instead of placing loading, debugging, profiling, editing and persistence in one larger `LuaManager`.

| Responsibility | Owner / proposed boundary |
|---|---|
| Module/asset identity and dependency metadata | Existing catalog/resource services plus `ScriptAsset` and `ScriptModuleDescriptor` |
| VM lifecycle and native context | `LuaRuntimeContext`: domain ID, state generation, allocator, bindings, source registry, diagnostics and shutdown state |
| Execution and scheduling | `ScriptExecutionService`: owner task, request queues, callback contracts, coroutine/task lifecycle and budgets |
| Instance and callback references | Generation-checked `ScriptInstanceHandle`/callback handles; registry references are private to the owning context |
| Editable/persisted state | `ScriptClassDescriptor` and `ScriptPropertySchema`, using existing `Properties`, scene/prefab serialization and asset references |
| Replacement | `ScriptReloadService`: dependency selection, staging, migration, bounded commit and retirement |
| Debugging | `ScriptDebugService`: breakpoints, hooks, stops, frames/scopes/values and bounded request processing |
| External IDE protocol | `WorkphoneLuaDebugAdapter`: protocol translation/launch/attach; no direct access to a live `lua_State` |
| Editor tools | Existing Lua-first authoring layer and native source/debug/diagnostic services; both Editor and VS use the same debug semantics |

Recommended target: separate trusted **Editor** and **gameplay** VMs. A stopped gameplay VM must not stop the Editor's own Lua tools. Keep Editor bindings on their supported owner task; use a dedicated gameplay script executor with explicit snapshot/command bridges to application/scene/physics/render owners. M0 must prove the binding and scheduling cost before committing that migration. Concurrent owners are forbidden while `LUABIND_NOT_THREADSAFE` and global callback routing remain unresolved. Merely creating two VMs is insufficient.

Use one documented lock order and avoid synchronous cross-task waits during callbacks, reload or debug stops. Native getters use safe snapshots or verified owner access; mutations use typed commands committed at a defined simulation boundary. Preserve same-tick gameplay semantics where required and document latency for async requests. Audit bindings individually; do not silently move all existing direct native calls to a worker thread. Start with a narrow real sample and expand the supported binding matrix. If M0 cannot establish concurrent Luabind safety, keep VMs on one real thread and implement a proven resumable execution boundary before certifying responsive in-process debugging; an isolated debuggee process is the bounded fallback, with its limitations stated.

Further per-world VMs are R2. Plugin bindings register before first module execution and carry ABI/capability/version metadata. Late registration and plugin unload require a safe barrier; no Lua closure/userdata may call into an unloaded DLL.

### 4.2 Protected execution and diagnostics

Provide `ScriptResult<T>` with success/error/cancelled/unsupported and a diagnostic ID. Preserve legacy `Parameters` callbacks explicitly: existing code passes a Parameters container and sometimes an output container, not ordinary Lua positional arguments and return values. Add a separately named direct-call API for positional arguments/multiple returns; never reinterpret the old ABI silently.

Every supported load/call/constructor/property/event/evaluation boundary must:

1. Validate context state, owner task, input limits, instance generation and native-object liveness.
2. Save and restore stack height; keep intended return values only in the explicit return adapter. Avoid C++ cleanup objects in frames that a Lua long jump can bypass.
3. Compile using explicit byte length and a stable named source, then execute under a protected boundary. Handle non-string error objects, OOM and errors in diagnostics/finalizers with allocation-bounded fallback reporting.
4. Capture error text and traceback before unwinding; attach source/hash, domain/generation, actor/component ID, callback, tick and severity.
5. Apply a documented failure policy: optional missing callback is a normal absence; a required missing callback is an error; a faulty gameplay instance is disabled/quarantined according to policy while other instances continue. Construction failures never publish partial instances.

The Lua manual documents protected calls, pre-unwind message handlers and distinct value/call stacks. Its C API also has long-jump and hook-yield constraints; verify the bundled fork against those rules before relying on C++ catches or coroutine suspension. [Lua 5.5 manual](https://www.lua.org/manual/5.5/manual.html#4.4).

Use bounded structured diagnostics shared by runtime, Editor Problems/Console and IDE output. Add duplicate suppression, severity/category/source filters, click-to-source, retained original error data and an exportable session log. Capture `print`/warnings through a safe bounded sink without recursively executing faulty user formatters. Unknown APIs and unsupported features must be visible, not successful no-ops.

### 4.3 Sources, modules, assets and packaging

**Lua scripts are first-class assets and resources.** Treat authored source, compiled modules and live execution as distinct layers of the existing system:

| Layer | Representation / responsibility |
|---|---|
| Authored asset | A `.lua` source file with a stable catalog UUID and versioned import/module metadata; source hash, exports, declared dependencies, domain/capabilities, schema and diagnostics. Editor asset operations preserve identity and version-controlled authored data |
| Compiled runtime resource | An immutable validated source/bytecode module resource produced by the existing compiler pipeline, keyed by asset identity, source/dependency hashes, target, VM/binding ABI and generation. Load once per context/generation where appropriate; share immutable data, not mutable Lua globals |
| Component reference and authored state | A scene/prefab Script component stores a typed script asset reference, exported class/entry point, schema version and property overrides. Keep class-name-only references as a migration path, not the durable authority |
| Live execution | A context-bound Lua module instance, component object, closures, subscriptions and coroutines. These have runtime handles and lifecycle; they are not serialized as resources or shared between Lua states. Recreate from resource plus approved authored/migration state |
| Development symbols | Source revision/hash, line mappings and optional source content associated with the compiled resource generation. Editor/VS breakpoints resolve against these records, not a guessed basename |

A source asset can export several classes/functions, with stable export identifiers and documented renaming/migration. A library module need not be attached to an actor to be an asset. Loading/compiling a resource must not implicitly execute arbitrary gameplay: instantiate/execute only through the owning runtime's declared entry point. Preserve missing-script references and overrides so a temporarily unavailable resource can be repaired. Extend the existing catalog, ResourceSystem, compiler registry and typed reference mechanism; do not create another script-only database, filesystem or packaging cache.

- A source record has asset UUID, canonical project/engine-relative URI, module ID, content hash, revision, compiled generation and retained source or symbol-sidecar reference. Identical basenames in different folders remain distinct. Generated/in-memory chunks receive explicit virtual IDs.
- Replace recursive execute-every-file bootstrap with engine/editor/project entry-point manifests and a project-scoped `require` searcher over the existing VFS/resource system. Declare eager bootstrap dependencies; record dynamic dependencies where possible. Detect missing modules, cycles, duplicate module/class exports and wrong domain capabilities. Do not globally lowercase identities; follow the shared asset path policy.
- Exclude tests/templates/legacy scripts from shipping entry points. Support a bounded compatibility manifest for existing globally registered `class 'Name'` scripts and existing `include` calls. Diagnose order-dependent globals instead of relying on filename sorting.
- Store class/module identity and schema in scene/prefab data as asset references plus compatibility names. Rename/move updates identity mappings and references, not the meaning of an unrelated same-named class.
- Reuse catalog/resource compiler, compilation database, dependency hashes and generation publication. Cook validated source or bytecode with exact VM version/build/numeric/architecture/endianness fingerprints and binding API version. Reject incompatible chunks before loading. Development retains source/line data; shipping stripping and separate symbols are explicit configurations, with debugger source/hash matching.
- Packaged runtime uses declared resources and does not scan the developer checkout or require an authoring database. Source-hidden packages are a supported distribution mode, not an encryption/security guarantee. Reproducibility and failure behavior are checked on a clean machine/directory.

### 4.4 Components, properties, events and async tasks

Define an instance state machine: unloaded → preparing → created → enabled → started → running/paused → disabled → destroying → unloaded, with an explicit failed state. Publish callback ordering for add/remove, enable/disable, reparent, actor activation, scene activation, project switch, Play/Stop and reload. Construction, enable, start, disable and destroy are exactly once per corresponding transition. Constructor side effects cannot substitute for a documented start callback.

R1 callbacks include create/load, enable, start, fixed update, update, late update, disable/unload, destroy and authoring validate/reset hooks. Route input, UI, collision/trigger, animation and application events through existing engine events with typed payload adapters. Specify update delta/fixed delta, time scale, ordering/dependencies, paused behavior and edit-mode opt-in. Preserve `__init`, `update`, property callbacks and Editor load/show/hide through adapters.

Subscription, timer, coroutine and async-operation handles belong to an instance/domain generation and cancel on destruction, incompatible reload, Stop and project switch. Completion returns to the script owner and never resurrects an unloaded instance. Support wait-for-time/frame/event/task, cancellation, timeout, failure propagation and coroutine tracebacks; distinguish game time from real time and freeze game waits on pause. Native callbacks cannot start untracked reentrant Lua execution.

Property schemas define stable field IDs, display names, types/defaults, validation, grouping/help, ranges, enums/flags, read-only/runtime-only fields, arrays and nested records. R1 includes bool/int/float/string, vectors/quaternions/colours, enums, actor/component and asset references; R2 adds richer containers/conditional UI and migration tooling. Persist only schema-approved data. Unknown fields remain recoverable through migration; missing scripts preserve their serialized data and show a repairable placeholder. Never serialize raw userdata/pointers/functions/threads.

Apply property changes through existing undo/redo commands and project dirty tracking. Support multi-selection, prefab overrides/revert, duplication/reference remap, saved defaults and live-runtime overrides with an explicit Apply-to-authored action. Type/class changes stage validation before replacing state. `getProperties` should not run arbitrary destructive gameplay code merely to draw an inspector.

### 4.5 Reload and failure recovery

Reload is a request/result operation, independent of garbage collection. File watcher events are debounced/coalesced and carry source revisions; manual and automatic reload share the service. The Editor shows progress, changed dependencies, diagnostics and the committed revision.

1. Determine the affected dependency set and validate source/schema/API compatibility. Pin the last good generation and reject stale project/source requests.
2. Compile into a candidate domain/generation. Capture only supported state through versioned save/migrate hooks. Native constructors/migration in staging cannot mutate the live world: use restricted capabilities, deferred command intents or owned reversible allocations.
3. Prepare replacement instances, validate references and callable caches, restore approved properties/state, and check required dependencies. Prohibit irreversible IO/network/audio gameplay side effects before commit. General arbitrary Lua side effects cannot be made transactional merely by catching an error.
4. At a documented safe boundary, quiesce affected execution, publish the complete replacement and command journal, rebind host handles/debug breakpoints and retire old callbacks/tasks/references while the old state is still alive.
5. On precommit failure, dispose candidate allocations and keep the previous generation active. Define bounded recovery for commit-time native failures; do not promise rollback of external irreversible effects. Record retained and rejected source hashes.

R1 may replace the whole gameplay domain transactionally; it must preserve the Editor domain and clearly classify runtime state that can be migrated. R2 adds selective dependency-aware replacement. Active coroutine stacks/closures cannot be copied into another state: cancel/restart according to a documented policy and notify the user. Reload during a stop is an explicit state transition that invalidates old frames/values; initially queue until continue or perform a visible restart. Never silently keep stale watch/frame handles.

Editor safe mode is native enough to open a project, view diagnostics, disable a faulty script/extension and restore a last-good revision when the Lua authoring layer itself fails. Recovery must not depend on executing the broken Editor script.

## 5. Comprehensive debugging design

### 5.1 Protocol and runtime backend

Use one Debug Adapter Protocol (DAP) adapter for external IDEs, backed by the runtime debug service. The current newline JSON model is not DAP and lacks request correlation and responses. Keep any internal transport small, versioned and tested; do not implement separate debugger engines for Editor and VS. DAP defines request/response/event exchange and reference-based inspection, while the adapter translates the runtime's own capabilities. [DAP overview](https://microsoft.github.io/debug-adapter-protocol/overview.html).

The runtime service owns a state machine covering disconnected/attaching/configuring/running/pause requested/stopped/stepping/reloading/terminating. Hook dispatch is shared with instruction budgets and profiling so one feature cannot overwrite another. Install hooks for each supported coroutine and handle call/return/tail-call/line/count events, source changes and repeated lines.

Network threads parse bounded frames and enqueue requests only. Live stack/locals/upvalues and mutations run on the Lua owner at a valid stop. Debug handles contain session, runtime generation and stop epoch; invalidate them on resume, reload, detach and destruction. Pause never waits while holding locks needed by UI/render/physics or by the transport.

Define world pause separately from Lua line stepping: physics/game time/gameplay events freeze coherently, rendering and Editor controls continue, and resume resets wall-clock accumulation so simulation does not catch up by minutes. Lua stepping does not advance a physics tick; frame-step is a separate action. Blocking native functions cannot be interrupted safely by a Lua hook; provide cooperative cancellation/timeout at their service boundary and report the pending pause accurately.

| Capability | R1 | R2 / acceptance detail |

The adapter must negotiate capabilities honestly. Cover initialize/configuration, launch/attach/disconnect, breakpoint replacement, execution control, threads/coroutines, stack/scopes/variables, evaluation and events using the selected DAP version. Do not advertise hover evaluation, variable setting, conditional breakpoints or paging before they work. Use standard DAP framing at the IDE boundary and explicit request cancellation/timeouts. [DAP specification](https://github.com/microsoft/debug-adapter-protocol/blob/main/specification.md).

Evaluation is development-only and opt-in. Default watch/hover inspection uses raw bounded access and safe native summaries; even `tostring`, table indexing and engine property access can have side effects. Reject arbitrary code in read-only evaluation rather than pretending a proxy environment is a secure sandbox. Full trusted REPL execution is a separate operation with explicit limits; instruction hooks alone do not bound blocking native calls.

## 7. Performance, resource limits and trust

Track VM allocation bytes/high-water mark, per-instance/callback cost, collector work/pause duration, pending requests, events and coroutine count. Use bounded queues, frame/message/value limits and backpressure. Cache validated callback references by generation; avoid repeated reflection/string lookup and temporary allocations in hot update paths. Benchmark the actual production binding path as well as empty Lua loops.

Set explicit per-project budgets and failure policies for instruction/time/memory use, event recursion, coroutine fan-out and log floods. Handle allocation failure and stack exhaustion without relying on allocating a large traceback. Count hooks are cooperative and cannot safely interrupt arbitrary native calls; services need their own cancellation/timeout. Avoid promising hard real-time or hostile-code isolation from Lua instruction limits.

R1 scripts are trusted project/Editor code. Offer narrower gameplay capability tables and VFS-scoped loaders; do not expose arbitrary OS/process/DLL/IO access simply because `luaL_openlibs` currently enables standard libraries. This is defense in depth, not a secure hostile-mod sandbox. Hostile plugins/mods need process isolation and a separate resource/IPC design.

Debug endpoints are disabled by default, development-gated and loopback-bound. Authenticate sessions, use per-session tokens and transport limits, avoid tokens in logs, and define one controller. Remote mode is R2 and explicitly enabled with authenticated encrypted transport or a secure tunnel. Shipping builds must prove that listener/evaluation paths are absent or inaccessible under the declared policy.
