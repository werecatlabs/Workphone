## Implemented runtime changes

- `MaterialShaderParameterLayout` owns immutable parameter metadata, defaults, a sorted stable-ID lookup table and cached built-in bindings. Registered shader instances retain this layout instead of copying names/descriptors. Instances borrow layout defaults; authored parameter copies share a value payload until an effective write detaches it, preserving independent value behavior.
- Parameter handles carry a unique layout identity and slot. Typed resolution/access distinguishes float, signed/unsigned integer, bool, colour, vector, matrix and resource kinds. Invalid/stale/cross-layout/type/size/offset operations are rejected in every build. Values remain packed CPU bytes accessed through copies, independent of GPU packing.
- Parameter instances expose effective-write revisions and name-lookup/storage counters. Built-in PBR bridges use cached semantic handles. Serialization iterates slots directly; names remain at the asset/editor boundary.
- Standard material settings have numeric IDs and table-indexed access. Built-in controls now use these IDs directly; the existing named editor API resolves a setting once at the authoring boundary and shares the numeric access implementation.
- `MaterialPassStateData` publishes a retained immutable `MaterialRenderState` when its outer write lock closes. Nested writes coalesce into one version; unchanged values reuse the current version. Cold authoring changes do not rebuild the runtime record. Existing `SafePtr` mutation paths participate without requiring each caller to maintain a second dirty flag.
- The five shader-name/path/keyword buffers live in a lazily allocated authoring block. They are absent from render snapshots and consume no text-buffer storage on an unconfigured pass.
- Materials cache primary-state selection by graph revision. Technique/pass creation, replacement, removal, generic child edits and pass/context lifecycle invalidate selection. New/unselected authored materials preserve their available primary pass behavior.
- DX11 mesh draws read one immutable snapshot for surface values, flags, sampler controls and texture objects. Standard and extension texture-unit edits update snapshots at edit time. Native views are obtained through the existing texture adapter, preserving delayed readiness, render targets and device-owned resource behavior.
- DX11 prepares material constants, packed-map slot selection and sampler controls in a persistent generation-checked table per renderer. Stable pages retain records across frames/views beyond the 128-entry four-way front cache. Warm resolution allocates nothing and compares weak ownership as well as addresses to reject address reuse. The table neither owns snapshots/textures nor stores device views. Publications lease table storage while retaining their own captured snapshot/resource owners. Snapshot texture objects are borrowed during draws instead of incrementing their reference counts for each texture lookup.
- Cached DX11 constants contain only eight material vectors. Lookup tags sit together within each set, separate from prepared values. A last-used index handles consecutive draws of the same snapshot; other warm hits compare addresses and ownership identities without inspecting strong-reference counts. Draw composition copies three contiguous material groups and initializes the view/draw fields explicitly. The shader constant-buffer format remains unchanged.
- Roughness modes 2 (metallic alpha) and 4 (inverted smoothness alpha) retain their established metallic-texture slot 2 routing. The initial preparation-cache integration had incorrectly left those modes on the separate roughness slot 3; this continuation restores the original draw-path behavior. All six authoring modes now have explicit CPU and renderer-adapter routing coverage, including repeated cached draws and delayed native-view readiness.
- Native material storage separates compact surface values from optional texture names. Empty slots allocate no strings; populated names allocate their actual bounded lengths. The existing size-tagged C descriptor is reconstructed on demand, and a new size-tagged bulk surface API avoids copying texture-name storage during synchronization. Native synchronization skips unchanged snapshots/revisions.
- Compatible parameter values survive reordered/extended shader schemas and partial updates; type changes use new defaults. An invalid candidate layout preserves the previous shader/layout/value state. Runtime handles are never serialized.
- Optional legacy pending values preserve metalness, roughness and opacity through first-pass creation and loading. Compatible canonical PBR values seed passes from the shader buffer instead; transfer releases each legacy field and frees the block after its final field retires.
- Material-owned parameter buffers now publish supported built-in edits automatically, including writes through retained mutable references. A changed-semantic mask preserves unrelated legacy edits, while the explicit full-apply API remains available. Rendering continues to consume immutable snapshots rather than reading mutable parameter bytes.
- `MaterialShaderParametersInstance::Edit()` coalesces nested edits into one snapshot publication per affected pass. An explicit full apply inside the scope is deferred too. Each commit walks the graph once, keeps existing virtual pass setters and opacity/render-mode normalization, and uses numeric setting IDs for scalar aliases. Schema construction and explicit PBR import suppress feedback; property restoration batches its writes. Edits made while no passes exist are retained for loading.
- Publication ownership belongs to the physical buffer instance: copies and moved values are detached, assignments retain the destination binding, and moved-from owned buffers can be reset and reused. Effective assignment advances the destination revision. This adds one non-owning pointer per parameter instance and no binding allocation; edit bookkeeping lives on the material.
- The Editor parameter listener no longer follows each numeric edit with a duplicate full renderer apply. Existing shader-selection and texture-loading paths remain in use.
- Validation exposed an existing scene-capture failure: native object attachment/detachment updated the owner chain without the graphics lock. Those operations now use the existing recursive graphics lock, preserving captured owner chains until rendering releases them.
- Native DX11 scene jobs now capture a dense table of material records for the union of main-view meshes and shadow casters. Section bindings contain 32-bit record indices; each distinct material contributes one retained snapshot/owner and one prepared record per publication. Hot records and cold ownership arrays are separate. Material-identity entries are cleared at sealing; their bucket/node capacity can serve the next publication.
- Scene colour/shadow submission borrows these records without reacquiring mesh materials, snapshot references or per-texture owners. Binding validation rejects another publication, retired/reused storage, a different mesh and changed section counts. Existing native culling, ordering, geometry submission and per-draw texture-view readiness remain in use. The renderer's bounded preparation cache feeds publication, so unchanged resident snapshots need no preparation, and even a publication larger than that cache does not thrash it between passes.
- A scene can recycle one empty retired record workspace after its final consuming borrow ends. Clearing it releases material/snapshot owners and invalidates bindings immediately, while retaining CPU array/map capacity. A held old job prevents recycling; its owners/storage retire normally after the last consumer. Scene clear, unload, native-scene release and destruction release the workspace capacity too.
- Owning-thread application, Editor and graphics updates now coalesce independent material setters through `MaterialPublicationScope`. Claw commits its CPU edits before capturing immutable scene jobs; edits outside a scope retain immediate publication. Live owner-side fallbacks preserve mixed legacy and typed values while render readers retain the previous snapshot.

## Compatibility and lifecycle boundaries

Existing material file keys (`ShaderParam.*`, `ShaderTex.*` and editor groups), public material/pass/editor methods and C descriptors remain supported. C++ consumers must rebuild against the changed headers and DLLs. Shader-name access within `MaterialPassStateData` now uses accessors over its private authoring block.

`Scalar`, `Vector2` and `Vector4` describe floating-point values explicitly. Integer shader parameters use `Int`, `UInt`, `IntVector2` or `IntVector4`; accidental same-size reinterpretation is rejected. Manually constructed offset/stride handles must be replaced with resolved layout-qualified handles. Unregistered custom layouts can be shared explicitly through `Reset(layout)`; registered shader instances share them automatically. Registry descriptor pointers still must not be retained across registration changes; retained layout references have independent lifetimes.

Outside an update scope, the outer state-context write-lock close remains the publication boundary. Inside `MaterialPublicationScope`, it queues the pass for publication when the outer update scope commits. Direct writes to public numeric state fields must use the existing `SafePtr`/write-lock convention; detached authoring code can explicitly publish after initialization. Named/typed state setting methods also participate. Rendering retains immutable versions, so readers can finish using an older snapshot while edits publish a new one. There is no global history retaining every edit.

Snapshots retain CPU texture objects, not native SRV pointers. They therefore do not replace the texture/resource manager, introduce a competing device cache or require materials to know when a texture view is recreated. Native texture-view lookup/preparation remains a separate optimization and validation boundary.

The DX11 preparation cache is owned by the graphics thread. Its fixed object storage is **24,848 bytes per renderer that draws snapshot-backed materials**, with at most 128 weak ownership records. This is 42.6% less than the initial 43,272-byte cache; each prepared value falls from 312 to 168 bytes. Weak references can retain shared-pointer control/allocation storage until eviction or renderer destruction; they do not retain the snapshot's live texture references. Cache collisions cause correct re-preparation rather than growth. Lighting, camera, fog, reflection environment and actual texture readiness are composed per draw and are absent from cached constants. A material edit publishes a different snapshot, which is prepared independently even if its pass-local revision equals another material's revision. Native-view lookup and the existing combined constant-buffer upload path remain active.

Parameter writes and edit scopes require owning-thread use or external synchronization, and the instance must outlive its edit scope. Buffer bytes/revisions update immediately; snapshot publication waits for the outer scope. A renderer reader can continue using the prior immutable version. The automatically projected semantics are the existing Albedo/Metalness/Roughness/Emissive/Opacity/AlphaClip/Color workflow mappings; custom CPU slots retain their values and revisions for serialization and future program bindings. Explicit `syncPBRToShaderParameters()` remains the import from legacy pass state. The update scopes coalesce independent high-level edits on their owning thread; removing duplicated legacy/authoring values remains open.

Scene material records share the existing native render-job lifetime. The active DX11 frame driver captures them during CPU preparation, before binding an offscreen target, and includes their elapsed work in total preparation timing. Explicit callers that prepare only culling can capture materials at the first DX11 submission instead. A material edit after capture appears in the next publication; retained jobs keep the prior values for both colour and shadow consumers. Discard/replacement, scene clear and exception cleanup release ownership through the existing job lifecycle. A publication identity qualifies mesh ranges and changes when storage is cleared; raw pointers and runtime indices are never serialized.

This table covers the native scene mesh path. Direct preview/UI/instance draws retain their existing immediate resolution and bounded cache; terrain and foliage retain their existing adapters. Third-party materials without a published snapshot retain the interface fallback and its live getter behavior. Records own no native views, so streaming completion and device recreation still use the texture adapter at submission. Per-job lookup maps/vector capacity are additional CPU storage; this is not a claim that total scene memory falls by the parameter-layer percentage below. This paragraph records the earlier checkpoint; the persistent table and direct-adapter migration are completed in the later M3 section below.

## Selectable scene draw sorting

`ClawScene::setDrawSortStrategy(strategy, bucketSize)` selects the ordering for subsequent DX11 main-view material publications. `QueueOrder` remains the default. Invalid strategies and nonfinite/nonpositive bucket sizes return false and preserve the current publication; equal assignments also preserve it. A changed policy retires the scene's active publication through the existing ownership path. The policy is an owner-thread runtime option and is not serialized.

| Strategy | Opaque ordering | Transparent ordering |
| --- | --- | --- |
| `QueueOrder` | Existing queue/z-order/submission sequence | Existing sequence |
| `FrontToBack` | Increasing camera-forward depth, then material | Back-to-front |
| `MaterialFirst` | Dense captured material ID, then depth | Back-to-front |
| `DepthBuckets` | Increasing depth bucket, material, then depth | Back-to-front |

For example, `scene->setDrawSortStrategy(ClawDrawSortStrategy::DepthBuckets, 10.0)` groups materials within ten-world-unit depth ranges. Sorting uses captured snapshots and integer material indices; it performs no name lookup or material/resource reference acquisition. Numeric key and permutation arrays retain reusable capacity in the existing material workspace. Their capacity is included in the table's storage counters. The default mode allocates no sorting buffers.

Reordering operates only inside contiguous eligible runs with the same render queue and explicit z-order. Unknown state, mixed section materials, refraction, UI/overlays, nonstandard depth comparisons, opaque materials without depth writes and nonfinite depths are barriers that keep their positions. Missing cameras preserve order. All sections must share one captured record to make a mesh eligible. Depth uses the captured camera and world transform's object origin, so intersecting transparent geometry still needs content-specific ordering. Shadow views retain their existing ordering.

The native `wp_graphics_cull_result_create_ordered` API validates a complete visible-index permutation and returns a separately owned immutable view sharing captured geometry. Source views and retained consumers remain unchanged. A changed order allocates a result wrapper, index array and temporary validation bytes outside the material-table counters; unchanged order avoids this copy. Existing native sort/phase counters describe original culling, while the extra scene ordering time belongs to material preparation. This does not establish allocation-free scene preparation or reduced draw/upload counts.

Contracts cover exact orders for all four modes, repeated-key stability against a reference sort, queue/z-order/barrier boundaries, invalid policies, frozen material classification after live edits, translated-camera depth, mixed-material barriers, warmed buffer reuse and no-camera fallback. Native contracts cover malformed permutations, independent view destruction, derived views and empty captures. WARP readback compares every optimized policy with a separately specified far-before-near alpha reference, and confirms that the unsorted near-first fixture produces different pixels.

## Reusable scene material storage

`ClawMaterialDrawRecords` now uses C++17 PMR containers with owner-thread storage. A small-block pool services map nodes; a backing cache retains chunks returned by MSVC's pool during clearing. Large record/owner/index vectors use direct counted allocation: superseded growth buffers are freed rather than accumulating in the chunk cache. Resource ownership is independent of allocator capacity. An empty workspace contains no live material/snapshot references, mesh entries or valid bindings.

The scene recycles storage only when it exclusively owns the retiring native jobs. A retained consumer forces a separate publication and keeps its previous resources intact. Temporary direct renders release their local borrow before recycling; cleanup cannot discard a newer publication created by a nested caller. At most one idle workspace is cached by each scene. External in-flight consumers can still retain their own old jobs. Clear/unload/native-scene release/destruction free the idle workspace; there is no new global storage or retirement queue.

Debug and optimized contracts exercise 384 materials and 768 section bindings over 32 reuse cycles, replacing all mesh identities every fourth cycle. After warm-up, the storage allocation count and retained bytes remain unchanged. The WARP scene contract checks held-old-job safety, zero-allocation exclusive reuse, temporary-render reuse and capacity release on unload, while preserving the prior captured red/updated green pixel checks.

Storage counters report actual upstream allocation requests, retained bytes and peak bytes for the table. Byte counts include allocated pool metadata, cached chunks, lookup buckets, vector capacity, backing headers and alignment padding. They exclude inline table/resource objects, material/snapshot/texture objects, native culling, GPU resources and the underlying allocator's bookkeeping. They measure table-storage allocation, not all engine/scene heap activity. Capacity is retained to the workspace high-water demand until an explicit scene lifetime release.

### Legacy and mixed edit batches

`Material::batch(const std::function<void(Material &)> &)` groups independent legacy and typed edits into one immutable snapshot publication per existing authored pass. The opacity, render-mode, surface-flag, scalar-specular, UV-tiling and UV-offset compound setters use this path internally. Nested batches reuse the outer pass scopes and parameter edit scope. Four pass write scopes fit in inline storage; larger graphs use an overflow vector. The outer batch holds pass write scopes through the deferred typed apply. Typed opacity and partial-schema fallbacks read current owner-side values once through the cached primary selection, preserving legacy edits that are absent from the intentionally older published snapshot. This fixes a reproduced failure where a typed opacity edit restored the previous RGB after a legacy colour change in the same batch. The live fallback read resolves no setting names and releases its read scope before writing.

Use the material batch as the outer scope when mixing edit APIs. An enclosing parameter-only edit scope can defer its typed commit until after the material batch closes. Pending typed values apply after the callback's legacy edits. A batch is not a rollback transaction: callback exceptions propagate after completed edits publish during unwinding. Empty/no-op/net-zero batches retain their snapshots; acquiring a batch does not clear preexisting dirty flags or mark clean states dirty. Changed setters retain their existing dirty-state behavior.

This is an owning-thread API. Renderer readers retain coherent immutable versions for each pass; separate passes are not one globally atomic publication. Only pass states present at batch entry are held. New graph states retain their existing publication behavior, and unloaded graphs are not resurrected by editing pending values. There is no global registry or new persistent resource ownership. The later update-boundary integration below also coalesces independent calls outside an explicit material batch.

## Update-boundary publication

`MaterialPublicationScope` groups independent setters on the current thread. Application and Editor update callbacks own a scope, committing before calling graphics update on the render task. Base graphics update groups load/unload queues and scene updates. Claw owns the outer graphics scope and explicitly commits after its UI/debug updates and before `prepareFramePasses()` captures material records. Post-render edits and standalone calls retain immediate publication. This preserves the existing C89 update/render frame driver.

State writes retain their normal short recursive locks. Closing a write scope queues a temporary strong owner instead of allocating/comparing a snapshot at every independent call. A fixed 256-entry pointer filter suppresses common duplicates; outer commit sorts/deduplicates the contiguous pointer vector and publishes each pass under its own state lock. Collisions affect queue size rather than correctness. Unchanged/net-zero values keep their existing snapshot. Live owner-side fallback reads in the PBR/typed bridges preserve pending legacy RGB and other unrelated edits.

Nested update scopes share the outer queue. Explicit material/parameter batches inside an update still work. If an update scope closes inside an existing state write or material batch, that enclosing write retains its final publication boundary. Commit releases temporary owners, including retired graphs, after state locks release. Ordinary queue capacity is reused up to 4,096 entries; larger burst allocations are discarded. The per-thread fixed storage and retained vector capacity are reported by `retainedStorageBytes()`. No fields or persistent owners are added to each material/pass.

This is an owning-thread boundary, not a global transaction across update threads or authored passes. Parameter buffers still require owning-thread use or external synchronization. A scope must be nested normally on its constructing thread and end before render capture. Render readers intentionally retain the previous immutable version during the update; CPU material getters read live values. Construction always publishes a valid initial snapshot; subsequent stack-state edits may defer, and stack destruction cancels its entries before the storage expires. A trivial TLS pointer guards queue teardown. Queue-allocation failure falls back to immediate publication; snapshot allocation errors propagate from explicit commit and are logged at a noexcept scope exit.
